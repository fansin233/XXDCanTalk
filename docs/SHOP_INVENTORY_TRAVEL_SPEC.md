# 会说话的西小电：商店、背包与出行开发规格

设计版本：1.0 · 日期：2026-09-29 · 基线：Godot 4.6.1 / 游戏 1.0.1

**文档状态：待实现的开发方案。** 下列价格、概率、时长是首轮调试初值，不能写成已经完成或已经验证的效果。建议在功能与手机验收完成后作为 1.1.0 发布。

实际项目目录为 E:/作品/XXD/XXDCanTalk/会说话的西小电/。文中的 res:// 路径均相对此目录。现有资源目录拼写是 Assests。

本规格负责商店、背包、出行及其必要的存档/UI 接入；与早期文档涉及这些系统的设想冲突时，以本规格为准。旧文档中的装扮、每日任务、离线三维衰减等设想不因此自动加入本轮范围。

## 1. 先固定产品规则

1. 星星是唯一购买货币。商品购买成功后先进入背包，使用时再消耗。
2. 三维明确指饱腹、电量、心情，范围为 0–100；经验沿用现有亲密经验。
3. 免费喂食、休息、抚摸继续存在。付费道具提供便捷恢复、额外经验和出行准备，资源用完仍能正常互动。
4. 同时只有一趟出行。点击出发后，在若干个随机时间节点寄回名片，最后自动到达归来状态。
5. 出行是独立的陪伴收集玩法。旅行中主界面的西小电仍然显示、说话、被触摸、吃东西和玩跑酷；旅行不扣主界面的三维，不改变角色动画状态，不检查饱腹或电量门槛。
6. 应用关闭后出行依旧按经过时间推进；下次打开补齐应到达的名片和归来事件。应用关闭时不要求实际运行游戏进程。
7. 名片到达、阅读名片、领取附件是不同操作。奖励领取成功后才进入钱包/背包，重开或连点都不能重复发放。
8. 图片先使用有辨识度的占位图，名片文字、物品、时间和奖励流程按正式功能实现。

玩家可见说明建议：“出行记录会在旅途中寄回，家里的西小电仍会陪你互动。”不需要用复杂剧情解释同一角色的两种玩法状态。

## 3. 本轮交付内容与游玩循环

最小完整版本交付：8 个可购买商品、可使用的背包、1 个可选便当槽、3 种常规旅程、1 次快速引导旅程、6 个目的地、18 张名片模板、6 种纪念品、收件箱、名片图鉴、3 档收集奖励。

~~~mermaid
flowchart LR
    A[说话 / 照顾 / 跑酷] --> B[小电星与经验]
    B --> C[商店购买]
    C --> D[背包]
    D --> E[恢复属性 / 增加经验]
    D --> F[可选便当]
    F --> G[出行]
    G --> H[名片到达收件箱]
    H --> I[阅读 / 领取附件]
    I --> B
    I --> D
    H --> J[名片图鉴与收集目标]
    J --> H
~~~

旅行不必购买便当即可开始。没有自动连续出发，也没有必须定时上线领取的过期奖励。

首轮不做：现金付费、卖回商品、背包格子扩容、道具耐久/过期、付费加速、抢救旅程、联网同步、系统通知、实时旅行地图和新增 3D 旅行场景。这些都不是完整闭环的前置条件。

### 3.1 首次体验

新玩家和升级的老玩家均一次性获得 12 星、丁香饭团×2、野餐便当×1；礼包标记与奖励在同一次存档提交中完成。重装保留存档、重开界面、迁移失败重试都不能再次领取。

引导顺序：打开商店看到价格和余额 → 购买一个商品 → 在背包查看实际效果 → 手动开始一次“校门散步” → 2–4 分钟内体验寄信与归来。步骤允许跳过，不能因此锁住主界面。

引导旅行独立于常规旅程，只能启动一次。2 张名片和最后归来共 3 段，每段随机 45–75 秒；总时长 135–225 秒。奖励固定为：

| 事件 | 名片/文字 | 附件 |
|---|---|---|
| 第一封 | campus_gate_01 | 1 星、丁香饭团×1 |
| 第二封 | canteen_01 | 1 星 |
| 归来 | “校门附近也藏着好多小发现，下次走远一点吧！” | 1 星、亲密经验 +4 |

引导不消耗便当、不增加或清零稀有保底计数。首次出发成功时保存 tutorial_trip_started，不能退出重刷。

食物和恢复品附带少量经验，保证三维接近满值时仍有可理解的用途。成长道具提供更高的纯经验性价比。免费基础喂食不扣背包物品，继续使用原来的恢复数值与照顾奖励规则。

沿用代码字段 hunger 表示“饱腹值”，数值越高越饱；不能按字面理解为“饥饿程度”而反向加减。

### 4.1 使用规则

- 饱腹、电量、心情结算后截断到 100。预览显示实际变化，例如当前饱腹 92，便当只显示“饱腹 +8”。
- 道具使用一次消耗一件；第一轮不提供批量使用，避免一次吃掉大量食物。
- 如果所有效果的实际变化均为 0，返回 NO_EFFECT，不扣道具。现有等级上限 10，但经验仍按现有逻辑累计；成长页须说明“当前等级上限 10，亲密经验继续记录”。
- 休息时禁止使用食物和恢复品，提示“先叫醒西小电再使用”；经验道具可用。面板不能悄悄唤醒角色。
- 物品消耗和属性/经验增加同一事务提交。成功后播放短反馈；动画被打断也不能撤销或重复结算。
- 背包食物不调用旧 feed()，否则会叠加免费恢复与每日照顾经验。道具只发配置表中的经验。
- 预览是说明，最终使用时必须按最新状态重算，不把预览中的数值直接写回。

## 5. 商店和背包交互

### 5.1 商店

商品卡展示图标、名称、单价、效果、已拥有数量；顶端常驻余额。点商品后进入详情，选择 1–99 件，展示总价，点击“购买并放入背包”完成。

数量默认 1，增加到无力购买的数量时明确显示差额。余额不足、商品失效、价格配置已更新或保存失败时都不扣币。购买成功后的提示为“已购买丁香饭团×2，花费 12 星”，可跳到背包。

价格只能从 Catalog 查询。UI 不传可信的总价、奖励或物品定义；数量是需要重新校验的请求值。保存未完成时禁用再次提交，并复用本次 request_id 处理重试。

### 5.2 背包

分类为全部、食物、恢复、成长、纪念品。同种物品按 item_id 合并数量，不占用多个格子。首轮没有收费容量和格子上限；计数使用整数，上限 1,000,000,000 仅用于数据合法性检查，溢出时拒绝整笔操作，不截掉奖励。

默认按类别、配置排序号、item_id 排序，不因为获得时间变化而不断跳格。点击条目展示效果、数量、来源说明和“使用一份”；纪念品只有详情，便当增加“去准备出行”的入口。

数量归零时移出可用列表。保留未知旧 item_id 的数量并显示“旧版道具”，不得直接删除；不能使用的原因要可见，后续补回定义可以恢复。

没有食物时仍可点“免费基础喂食”；没有星星时仍可出行。背包界面不同时直接显示所有隐藏的已解锁空物品。

## 6. 出行玩法的确定规则

### 6.1 旅程类型与奖励初值

每张常规名片一定附带小电星；“可能带回的道具”按下表独立抽取，不承诺每封都有物品。所有抽取在出发时完成并保存结果。

| 路线 ID / 名称 | 名片数 N | 每一段时间（含最后归途） | 总时长范围 | 每封名片星星 | 归来礼包 |
|---|---:|---|---|---|---|
| nearby / 附近散步 | 2 | 20–40 分钟 | 1–2 小时 | 固定 1 星 | 1–3 星、基础物品×1、经验 +6 |
| city / 城市漫游 | 3 | 45–90 分钟 | 3–6 小时 | 随机 2–3 星 | 3–4 星、基础物品×2、经验 +10 |
| faraway / 远方旅行 | 4 | 90–180 分钟 | 7.5–15 小时 | 随机 4–5 星 | 5–9 星、基础物品×3、经验 +16 |

常规每封额外进行两次互不排斥的抽取：

1. 35% 概率附带一件基础物品，物品池为饭团 50%、牛奶 30%、曲奇 20%。
2. 20% 概率附带当前目的地的一件纪念品。

归来的基础物品也按此物品池逐件抽取，合并同种数量。经验只在归来礼包中发放，常规名片本身不另加经验。

因此不计图鉴奖励，三种路线每趟总星星为 3–5、9–13、21–29；期望分别为 4、11、25。道具期望数量分别约 1.7、3.05、4.4 件基础物品，纪念品另计。

这些初值使常见商品可在一次主动会话或短旅行后购买，长旅行适合睡前安排。每日两趟短旅行加一趟长旅行的期望星星为 33；叠加现有主动奖励后的最高档期望约为 53。需通过完整会话调价，不能把期望数当作每个玩家必得数。

旅行首轮没有每日次数或奖励上限，但每趟结束都要玩家再次发起，绝不自动续行。密集上线者可多跑短途，这是单机陪伴游戏允许的节奏差异；若经济过快，优先调整配置表的奖励，不提高饥饿惩罚。

### 6.2 行前准备与便当

选择路线 → 可选一份野餐便当 → 显示预计时长范围、名片数、可能奖励 → 点击“出发”。

准备界面只保存选择，不提前扣物品。关闭准备页无成本。出发事务中检查空闲状态、物品数和配置，再消耗便当并保存整趟计划。

便当效果固定为：第一张常规名片的稀有概率从 10% 提到 20%，且归来多带一件基础物品。只作用于本趟，不能叠加；放入便当后不再给主界面加饱腹、心情或经验。

带便当追求收集与额外物品，不构成“花 14 星必定赚回更多星”的循环。旅行途中不能补放、替换或取回；初版不提供中途召回与取消。旅行即使应用关闭也会按原计划归来。

### 6.3 日程生成

常规旅程需要 N 张名片和 1 个归来事件，一共 N+1 段时间。

~~~text
elapsed = 0
对每张名片 i：
    elapsed += 在该路线每段最短/最长秒数之间均匀取整数
    固定目的地、模板、正文、稀有度与附件
    保存事件 id = trip_id + ":postcard:" + i，due_offset_sec = elapsed
elapsed += 再取一个随机归途时间
保存 id = trip_id + ":return"，due_offset_sec = elapsed，固定归来附件
~~~

时间必须严格递增，最后一个事件必须是归来。一个独立 RNG 实例生成本趟计划，不使用会被 UI 动效等消耗的全局随机状态。保存完整结果；随机种子仅用于排查，不作为更新后重算奖励的依据。

出发后查看页面、领取、重启、换版本均不重新抽取。调价和改概率只影响以后新出发的旅程。

### 6.4 旅行状态机

~~~mermaid
stateDiagram-v2
    [*] --> READY
    READY --> TRAVELLING: 出发事务成功
    TRAVELLING --> TRAVELLING: 某个名片节点到达
    TRAVELLING --> RETURNED: 最后归来节点到达
    RETURNED --> READY: 玩家确认已归来
~~~

准备界面是 UI 状态，不是已出发存档。RETURNED 表示时间上已经归来，“收好行李”只是确认与清理本次活动记录，不发第二份奖励。未领取旧信附件不影响再次出发。

有一项容量保护：待领取信件达到 200 封时，暂停开始新旅程，给出“全部收下”的操作。已经在途的名片、归来和收集奖励始终完整入箱，不因容量上限丢弃；因此允许短暂超过 200。

### 7.2 内容抽取与重复控制

目的地从路线池等权抽取，先打乱走一轮，用尽后重新打乱，并尽量避免连续同地。每处 2 张普通、1 张稀有；普通候选等权抽取。

普通情况下稀有概率 10%；便当仅让本趟第一张变为 20%。跨旅程记录 rare_miss_streak：连续 7 张常规名片未出稀有后，下一张保证稀有；出稀有清零，出普通加 1。引导名片不参与。

稀有判断后，在对应目的地和稀有度内优先选本趟未出现的模板；候选不足时尝试同路线其他目的地，再允许重复，不能为了去重把保底稀有降成普通。稀有计数在出发生成计划时更新，并与计划一起保存。

### 7.3 信件和领取

信件到达时生成唯一 mail_id，登记图鉴发现次数，再显示“西小电寄回了 2 张新名片”等合并提示；主界面不弹连续模态窗口。

点信件详情才标记已读。阅读不发奖励；点击“收下附件”把星星、经验、物品一次性加入对应模块，并同一次提交 claimed 标记。领取按钮提交中禁用，重复点击返回 ALREADY_CLAIMED。

“全部收下并标为已读”对当前待领取信件做一笔汇总事务，展示一份合并结果。红色数字显示待领取封数，新内容圆点表示未读，两个标记不相加。

奖励永久保留。已读且已领取的原始信件仅保留最近 100 封；更早的阅读内容由图鉴保留，图鉴为每个模板保存首次正文快照、首次/最近获得时间与累计次数。未读或未领取信件不能被清理。

### 7.4 收集目标

18 个模板均为独立图鉴条目；同一模板再获得只增加次数，照常领取该封固定附件，不额外兑换重复卡奖励。

| 不同名片总数 | 一次性收集奖励 |
|---:|---|
| 6 | 12 星、学习卡片×1 |
| 12 | 18 星、野餐便当×1 |
| 18 | 30 星、成长手账×1 |

达到门槛时创建 collection:6、collection:12、collection:18 三种固定 ID 的奖励信件。标记“此门槛已生成奖励信”和插入信件同一次保存；领取继续使用统一附件流程。收集奖励不算旅行名片，不推进稀有保底。

## 9. 配置数据：策划可改，代码负责校验

推荐使用以下小型 JSON 文件，启动加载一次。图片和音效用 art_key / sound_key 间接映射到导入后的资源，存档不保存 Texture2D、Node 或二进制图片。

| 配置文件 | 内容 |
|---|---|
| res://Data/items.json | ID、名称、分类、图标键、售价、排序、效果、可装便当标签 |
| res://Data/travel_routes.json | 名片数、各段时间范围、目的地池、星星范围、归来礼包 |
| res://Data/postcards.json | 18 个稳定模板 ID、目的地、稀有度、正文、图片键 |
| res://Data/reward_tables.json | 基础物品权重、纪念品映射、独立掉落概率 |
| res://Data/progression.json | 首次礼包、快速旅程、图鉴门槛、便当加成、保底参数 |
| res://Data/art_map.json | 图标/名片键到资源路径的映射和通用占位图 |

物品示例，字段即实现约定：

~~~json
{
  "id": "picnic_bento",
  "name": "野餐便当",
  "category": "food",
  "icon_key": "item_picnic_bento",
  "sort_order": 40,
  "buy_price_stars": 14,
  "effects": {"hunger": 35, "energy": 0, "mood": 8, "friendship_xp": 5},
  "usable_at_home": true,
  "requires_awake": true,
  "travel_supply_id": "bento_bonus"
}
~~~

所有 ID 一经发版不可复用为另一物品/名片；下架通过 enabled=false 保留定义。配置启动校验包括唯一 ID、有效引用、非负价格/奖励、合法概率和权重、时间上下限、至少一个可选模板。

raw JSON 需要明确加入导出资源。当前预设 include_filter 为空，开发时将 Data/*.json 合并进该过滤器，再核对安装包中的配置能读取；不要只依赖编辑器可见。[Godot 4.6 导出资源过滤说明](https://docs.godotengine.org/en/4.6/tutorials/export/exporting_projects.html#resource-options)

出行计划保存 content_version、正文与奖励快照，避免改配置后进行中的奖励变化。模板图片键失效时显示通用占位图；物品 ID 失效时保留数量与来源，不能丢奖励。

## 10. 代码架构与现有模块改造

采用一个权威状态、一套提交入口。当前 Main 已自行创建服务节点，继续使用显式创建和注入依赖；本轮不再增加一套平行的 Autoload 数据服务。

~~~mermaid
flowchart TD
    UI[HUD / 商店 / 背包 / 出行页面] --> S[ShopService / InventoryService / TravelService / MailboxService]
    P[PetState 现有照顾与成长入口] --> G[GameStore 唯一状态与事务]
    S --> G
    C[Catalog 配置] --> S
    T[TimeService 时间输入] --> S
    R[RewardService 奖励计算] --> G
    G --> V[SaveRepository 整体快照保存]
    G --> E[提交成功信号与只读快照]
    E --> UI
~~~

### 10.1 建议文件职责

| 新增/调整文件 | 职责 |

| Scripts/Services/ShopService.gd | 权威价格校验，扣星并加库存 |
| Scripts/Services/InventoryService.gd | 库存读取、使用预览、消耗物品并应用效果 |
| Scripts/Services/TravelService.gd | 出发计划、补齐到达节点、归来状态与确认 |

服务可以是普通 RefCounted 对象，不需要每个都有 _process()。GameServices 负责一个低频时钟；只在可见页面更新相应 UI。

### 10.2 启动顺序

1. Catalog 加载校验；SaveRepository 读取与迁移。
2. GameStore 装入一个完整状态；必要时提交首次礼包。
3. TimeService 结算当前一趟离线进度，TravelService 批量补齐到达节点。
4. 创建/注入 PetState、各服务、角色、声音、HUD，绑定信号并发布初始快照。
5. HUD 一次显示最新余额和未领取数量，合并离线提示。

PetState._ready() 不再自己加载旧存档；避免初始化时又把刚迁移的钱包覆盖回旧数据。UI 如果尚未连接信号，必须仍能通过 get_snapshot() 拿到完整当前状态。

### 10.3 服务接口契约

以下为目标 API，开发者可用具名 DTO 实现，而不是到处传任意 Dictionary。

~~~gdscript
# 以下只是接口规格，不是本轮已经新增的实现。
ShopService.get_offers() -> Array
ShopService.buy(item_id: String, quantity: int,
        catalog_version: int, request_id: String) -> CommandResult

InventoryService.get_items(category: String) -> Array
InventoryService.preview_use(item_id: String) -> ItemUsePreview
InventoryService.use_item(item_id: String, request_id: String) -> CommandResult

TravelService.get_snapshot() -> Dictionary
TravelService.depart(route_id: String, supply_item_id: String,
        request_id: String) -> CommandResult
TravelService.reconcile() -> CommandResult
TravelService.acknowledge_return(request_id: String) -> CommandResult

MailboxService.mark_read(mail_id: String) -> CommandResult
MailboxService.claim(mail_id: String, request_id: String) -> CommandResult
MailboxService.claim_all(request_id: String) -> CommandResult

GameStore.get_snapshot() -> Dictionary
GameStore.execute(command: GameCommand) -> CommandResult
GameStore.flush() -> SaveResult
~~~

CommandResult 至少包含 ok、code、request_id、save_revision、actual_changes；实际变化包含星星、经验、各物品数量与三维增量。成功信号包括 wallet_changed、inventory_changed、pet_changed、travel_changed、mailbox_changed，均在成功提交后合并发布。

UI 不能写任何 stars、inventory、claimed、travel 字段。内部读取可以使用受控引用，对外快照必须复制或保证只读。

| 错误码 | 玩家反馈或处理 |
|---|---|
| INSUFFICIENT_STARS | 星星不足，还差 N 颗 |
| NOT_ENOUGH_ITEMS | 道具数量已变化，请重新选择 |
| INVALID_QUANTITY / INVALID_ITEM | 请求无效，刷新列表；不扣资源 |
| CATALOG_CHANGED | 商品信息已更新，重新展示确认 |
| CHARACTER_RESTING / NO_EFFECT | 先唤醒 / 当前使用没有效果 |
| TRIP_ALREADY_ACTIVE | 已有一趟旅程，打开当前进度 |
| MAILBOX_FULL | 先收好邮袋里的附件，再安排下一趟 |
| MAIL_NOT_FOUND / ALREADY_CLAIMED | 刷新到实际状态，不发第二份奖励 |
| SAVE_FAILED | 无法保存，本次操作未提交，可重试 |
| SAVE_UNCERTAIN | 正在恢复存档状态；暂停新经济操作，完成恢复后展示真实结果 |

不把每秒属性变化的版本号当成 UI 的购买锁，否则余额没问题也会因一次自然衰减而购买失败。购买校验配置版本，并在执行时读取最新余额；单线程事务在内部串行化。

### 10.4 语音暂停令牌

增加 acquire_suspend(reason) -> token 与 release_suspend(token)，活跃令牌非空时不重启收音。reason 至少区分 overlay、minigame、character_feedback、app_background。

迁移现有笑声/小游戏的 suspend_for_feedback()/resume_after_feedback() 调用，使它们持有各自令牌。UI 详情和父页面共享一个由 OverlayHost 持有的令牌，不因关闭详情就释放父页面的暂停。

令牌只在运行时存在，不写入存档；自动模式的用户选择独立管理。cancel_all() 目前会关闭用户开关，因此不能不加区分地用它代替“临时打开商店”的暂停语义。

## 11. 钱包、物品与领奖必须整体提交

推荐事务流程：

~~~text
接收一个带 request_id 的命令，锁定本次执行
→ 检查同一请求是否已完成
→ 从当前权威状态复制草稿（包含最新三维与旅行时间）
→ 校验余额 / 库存 / 旅程状态 / 领取状态
→ 在草稿中完成全部扣除、增加、标记与必要的时间快照
→ SaveRepository 提交这份完整草稿
→ 成功：替换运行时权威状态，发一次信号，返回实际到账
→ 明确失败：保留原状态，返回失败
→ 无法确认：先恢复确定状态，再开放下一笔操作
~~~

四条必须成为同一事务的业务边界：

| 操作 | 同一事务中必须包含 |
|---|---|
| 买便当 | 钱包扣星 + 背包增加便当 |
| 吃便当 | 背包减少便当 + 三维变化 + 经验变化 |
| 带便当出发 | 背包减少便当 + 完整随机计划 + 出行序号 + 稀有保底计数 + 引导标记（如适用） |
| 收下名片 | 邮件 claimed 标记 + 钱包/经验/库存增加 |

禁止先保存扣星，再由 inventory_changed 回调发物品；禁止名片打开一次就自动调用奖励函数。动画、声效、提示均在成功后发生。

近期 request_id 结果可保留最多 256 条用于按钮重试；跨重启的重要去重依据是持久业务状态：mail.claimed、trip.delivery_cursor、唯一 mail_id、一次礼包标记、收集奖励生成标记。不能把有限长度的请求缓存当作永久领奖记录。

Main 中跑酷和复述结算也改为读取实际 CommandResult。例如第四局理论奖励 5 星但每日额度已用完，提示实际“本局未获得小电星，今日有奖次数已用完”，不能显示 +5。小游戏重复完成回调应带同一 run_id，并且只结算一次。

## 12. 时间、离线进度与手机生命周期

### 12.1 时间模型

旅行以“累计经过秒数 + 事件相对秒数”为真值。保存每个事件的 due_offset_sec，不用手机显示的日期直接决定是否能领同一份奖励。

前台用 Time.get_ticks_msec() 差值累计；存档和后台间隔使用整数 UTC 秒。Godot 的系统时间可能被调整，ticks 则保证单调；两者承担不同工作。[Godot 4.6 Time 文档](https://docs.godotengine.org/en/4.6/classes/class_time.html)

每趟保存 elapsed_sec、clock_checkpoint_unix 和最后事件的 total_duration_sec。ticks 的锚点仅保留在本次进程内，不跨进程保存后相减。

~~~text
前台经过时间：
    elapsed = min(total_duration, elapsed + (tick_now - tick_anchor) / 1000)
    tick_anchor = tick_now

从后台或冷启动恢复：
    offline_delta = max(0, wall_now_utc - wall_checkpoint_utc)
    elapsed = min(total_duration, elapsed_at_checkpoint + offline_delta)
    wall_checkpoint_utc = wall_now_utc
    tick_anchor = tick_now       # 从这里开始新的前台段

到达结算：
    按顺序扫描 delivery_cursor 指向的事件
    只要 due_offset_sec <= elapsed，就追加唯一信件并推进游标
    遇到归来事件则把旅程设为 RETURNED
    将本批信件、游标、图鉴与状态一次提交
~~~

同一进程恢复时使用暂停时的内存锚点；冷启动用磁盘锚点。每次保存前先把截至当时的前台 elapsed 一并更新，再保存对应的 wall_checkpoint。不得用旧 elapsed 配上新系统时间，否则会丢失进度。

恢复时只能补一次后台间隔，不能再把跨越后台的 ticks 差值加一次。先补进度再重设前台锚点；重复恢复回调由明确的 foreground/background 状态挡住。

### 12.2 校时和极端离线情况

| 情况 | 规则 |
|---|---|
| 正常在线 | 一个 1 秒低频调度即可；旅程最多 5 个事件，无需每帧查询系统时间 |
| 关闭游戏跨过多个节点 | 把本趟所有应到事件批量入箱；顺序与正文保持原计划 |
| 离线数天 | 最多完成当前一趟，不自动生成多趟奖励 |
| 系统时钟倒退 | 后台差值按 0 处理；不减少 elapsed、不回退游标；锚点重设为当前系统时间，继续正常计时 |
| 系统时钟前跳 | 最多提前完成当前一趟；不制造多次领取、不连锁出发 |
| 前台手动改时 | 前台 ticks 继续计时，不根据墙钟跳动突然补一大段 |
| 改时区 | UTC 差值不受本地显示时区影响；名片显示日期再转换 |
| 到达时保存失败 | 不发布已收信成功提示；保留待提交结果并重试，不重新抽奖励 |

这是离线游戏的容错设计，不能证明手机时间真实；首轮接受改时可能提前完成当前旅程，不宣称具备服务器级反作弊。旅行没有每日限额，避免与现有本地日奖励重置互相影响；现有主动奖励日计数迁移时原样保留。

### 12.3 生命周期函数

Main 把 NOTIFICATION_APPLICATION_PAUSED 转给 GameServices：结算前台时间、停止本轮 UI 动效/检测、提交脏状态；后台不会继续跑一个常驻计时服务。

收到 NOTIFICATION_APPLICATION_RESUMED 时：恢复锚点、补齐旅行、发布一次快照；麦克风是否恢复按用户设置和前台暂停令牌处理。桌面窗口关闭也调用同一个 flush()，不再访问 PetState 的私有 _save()。

手机应用可能在后台被系统结束，不能把桌面关闭窗口事件当成唯一保存时机。[Godot 移动端退出与暂停说明](https://docs.godotengine.org/en/4.6/tutorials/inputs/handling_quit_requests.html#on-mobile-devices)

购买、使用、出发、到达、领奖立即提交；单纯属性/旅行秒数可每 30 秒保存一次脏快照，并在切后台追加保存。新功能不申请定位、后台运行或通知权限；后续系统本地通知只能提醒，不能成为真正的奖励结算来源。

### 12.4 时间示例

09:00 开始附近散步，三段预先抽为 25、38、29 分钟：09:25 第一封、10:03 第二封、10:32 归来。

玩家 09:10 关闭应用，11:00 打开时一次补齐 2 封名片和 1 封归来信，显示“旅途已结束，有 3 份附件待领取”。11:01 重启不会再新增三封；到 12:00 也不会自己开始下一趟。

## 13. 存档 v2 与迁移细则

### 13.1 根结构

继续使用 user://pet_save.json，由 SaveRepository 一处维护。下面是新档完成首次礼包后的有效示例；数字日期仅表示格式。

~~~json
{
  "schema_version": 2,
  "save_revision": 1,
  "content_version": 1,
  "pet": {
    "hunger": 82,
    "energy": 78,
    "mood": 85,
    "friendship_xp": 0
  },
  "wallet": {"stars": 12},
  "inventory": {"rice_ball": 2, "picnic_bento": 1},
  "daily": {
    "key": "2026-09-29",
    "echo_rewards": 0,
    "care_rewards": 0,
    "minigame_rewards": 0
  },
  "travel": {
    "next_trip_sequence": 1,
    "rare_miss_streak": 0,
    "active_trip": null,
    "recent_history": []
  },
  "mailbox": [],
  "album": {},
  "flags": {
    "welcome_pack_granted": true,
    "tutorial_trip_started": false,
    "collection_rewards_created": []
  },
  "recent_command_receipts": []
}
~~~

等级仍由 friendship_xp 计算，不另存第二个可冲突的等级真值。休息与录音状态按当前主界面的运行时策略管理，本轮不会因为出行而增加离线休息/离线属性衰减。

### 13.2 必须具备的数据对象

| 对象 | 必需字段与约束 |
|---|---|
| RewardBundle | stars、friendship_xp、items: item_id→正整数；奖励不自动修改三维 |
| ItemEffect | hunger、energy、mood、friendship_xp；只用于主动使用物品 |
| TripPlan | trip_id、route_id、is_tutorial、content_version、seed_string、departed_unix、supply_item_id、state、elapsed_sec、clock_checkpoint_unix、total_duration_sec、delivery_cursor、events |
| TripEvent | event_id、kind=postcard/return、due_offset_sec、目的地/模板 ID、正文/图片键/稀有度快照、RewardBundle |
| MailRecord | mail_id=event_id 或 collection:n、来源 trip_id、kind、内容快照、计划到达时间、实际处理时间、read、claimed、RewardBundle |
| AlbumEntry | template_id、首次内容快照、first_received_unix、last_received_unix、received_count |
| TripSummary | trip_id、route_id、归来时间、名片数量；最近 20 条即可，未领取附件仍由 mailbox 持有 |
| CommandReceipt | request_id、命令类型、save_revision、结果摘要，最近 256 条 |

trip_id 由已保存的递增序号生成，例如 trip_000001；分配序号与出发一起提交，随机种子不能充当唯一 ID。已到达事件游标和信件必须同存，不能只依靠“列表里看起来已经有一封”判断进度。

JSON 没有独立整数类型，读取时要验证有限数值、是否为整数、合法范围，再转换为 GDScript int；不能把负数数量直接用于扣除。64 位随机种子存字符串，时间以秒计，避免超大数字精度问题。[Godot 4.6 JSON 文档](https://docs.godotengine.org/en/4.6/classes/class_json.html)

### 13.3 从真实 v1 迁移

1. 读取现有 pet_save.json / .tmp / .bak 的可恢复版本。先保留一份不被后续轮换覆盖的 pet_save.pre_v2.json。
2. 把 v1 顶层 hunger、energy、mood、friendship_xp 放进 pet，stars 放进 wallet。
3. 把 daily_key、daily_echo_rewards、daily_care_rewards、daily_minigame_rewards 映射进 daily。已用奖励次数不清零。
4. 新增空背包、旅行、信件和图鉴结构，维持旧经验与余额；首次礼包在同一迁移提交里额外加上 12 星及指定道具，并标记已给。
5. 提交 v2 成功后才允许 UI 操作新系统。迁移失败时保留 v1，可重试；重试不能再次累加已成功发过的礼包。
6. audio_settings.cfg、runner_best.cfg 继续使用，不重置音量和最高分。

普通重新加载 v2 不执行迁移、不再发礼包。只有所有候选文件都不存在才属于新玩家；存在但全损坏时进入恢复提示，不能静默覆盖为新号。检测到高于支持范围的 schema 时保留文件并提示版本不匹配。

### 13.4 提交与恢复

保留“正式文件 + 临时文件 + 备份”思路，但让 SaveRepository 返回确定结果并校验每一步错误：

1. 在内存生成完整、字段合法的下一版快照，revision 加 1，写临时文件并 flush/close。
2. 必要时回读校验 JSON、schema、revision、计数、唯一 ID 和事件顺序。
3. 轮换有效备份并提交正式文件，只有确定提交后才返回 COMMITTED。
4. 明确提交失败且新临时文件已安全移除时返回 NOT_COMMITTED；保留原权威状态。
5. 文件替换或清理失败导致不能确定是否已提交时返回 UNKNOWN，先恢复候选存档、按 request_id 和业务标记确定结果，期间不能接着执行新交易。

崩溃启动时可从完整临时文件恢复未显示成功但已经落盘的操作；按合法候选的版本与 revision 选择，并保留坏文件用于排查。完成恢复之前不接受新的购买或领奖请求。不要把“返回失败但遗留的新临时快照”当成可随意忽略的问题，否则下次恢复可能额外扣一次星。

任何恢复都只能得到整笔交易前或整笔交易后的状态，不能得到扣了星没物品、用了物品没效果或奖已发但 claimed=false 的混合状态。

## 14. 手机性能与资源约束

新增系统全部用轻量 2D UI 和小型数据驱动，不新增独立 3D 旅行场景。角色继续复用当前主场景的实例。

| 项目 | 首轮实现目标 |
|---|---|
| 调度 | 一个 1Hz 旅行检查；到达最多处理本趟 5 个事件，加最多 3 个一次性图鉴奖励 |
| 页面 | 打开时才构建/显示列表，关闭后不做每帧重建；长列表分页或复用条目 |
| 图片 | 6 张目的地占位图复用；详情图建议不超过 1024×640，列表使用缩略图/同一纹理 |
| 缓存 | 详情纹理按需加载，最多缓存 3 张；不为每封信复制纹理 |
| 存档 | 目标保持 1 MiB 内；只存文字/ID/计数，归档已读已领旧信 |
| 性能验收 | 新系统额外常驻内存目标不超过 25 MiB；低端目标机界面至少稳定 30 FPS |
| 文件写入 | 交易立即提交；其他脏数据低频保存，严禁每秒写一次整个存档 |

这些数值是验收目标，需实际测量。首批占位图和小图标优先用简洁 SVG 或低分辨率纹理；关闭面板不遗留 Node、Tween 或重复信号连接。

本轮不清理角色资产。xxd2.gltf 仍依赖 xxd2_head2.png、xxd2_body.png、xxd2_red.png、xxd2_贴图.png 及对应导入设置；正式导出需在资源依赖完整的工程上进行。现有手机胸口显示问题要单独回归，不能用这些 UI 功能的通过结果替代模型验证。
